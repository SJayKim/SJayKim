**vLLM 기반 텍스트 처리 API 서비스 (AI_LLM_API)** · Serving · Pipeline

기사 요약, 분류, 태깅을 각각 따로 처리하고 있었고, 외부 API에 의존하니 비용과 레이턴시가 계속 문제였음.
vLLM 엔진을 FastAPI 프로세스 안에서 직접 돌리는 방식을 택했다. 외부 호출 없이 in-process로 추론하니 네트워크 왕복이 사라지고, 토큰 레벨 연속 배칭으로 동시 요청도 효율적으로 처리된다. asyncio.Semaphore로 동시 연산 슬롯 수를 제한해서 GPU 메모리 초과를 방지.
LangGraph로 용도별 에이전트를 나눴다. 요약(SummarizationAgent)은 목표 길이 70~130% 안에 들어올 때까지 적응형 재시도를 하고, 긴 문서 축약(ReduceAgent)은 Map-Refine으로 불릿 추출 후 평문 변환. 키워드 추출, 다중 기사 통합 요약도 각각 별도 에이전트로 분리했다. API 버전을 v0/v1로 나눠서 기존 연동을 깨지 않고 LangGraph 기반으로 점진 전환.

6종 API 엔드포인트를 단일 서비스로 통합. Gradio UI도 붙여서 기획팀이 바로 써볼 수 있게 했다.

**Milvus 기반 Agentic RAG 시스템 (AI_PROMPT + RAG-Chatbot)** · Search · Safety

한국어 매거진 기사에 대한 질의응답이 필요했는데, 키워드 검색으로는 "여름에 읽기 좋은 글" 같은 의미 기반 질문에 대응이 안 됐다. 동시에 생성형 AI 응답에 대한 안전성 검증 체계도 없었음.
Dense 벡터(BGE-M3, 1024차원)와 BM25 Sparse 검색을 합친 하이브리드 검색을 짰다. 둘 중 하나만 쓰면 놓치는 게 있어서 — Dense는 의미는 잡는데 고유명사에 약하고, BM25는 그 반대. 검색 결과는 BGE-Reranker-v2-M3로 재정렬하고, 검색된 청크 앞뒤로 문맥을 자동 확장하는 컨텍스트 윈도우도 넣었다.
에이전트 흐름은 Safety Guard → Reasoning → Tool Calling → Response 순서. 입력은 LlamaGuard가 먼저 검사하고, 출력도 한번 더 거른다. SSE로 토큰 단위 스트리밍, Thread 기반 Checkpoint Store로 대화 이력 관리.
전처리에서 100자 이하 청크는 걸렀다. 너무 짧은 청크가 벡터에 섞이면 검색 노이즈가 된다. 특수문자 제거, KoNLPy 기반 토큰 검증까지 적용.

체크포인터를 MongoDB/PostgreSQL/SQLite 세 가지로 지원해서 운영 환경에 맞춰 골라 쓸 수 있게 했다.

**ReAct + Reflexion 자기 개선형 AI 에이전트 (MCP Host)** · Agent

에이전트가 Tool Calling에 실패하면 같은 실수를 반복하거나 그냥 멈춰버렸다. 사람이라면 실패 원인을 생각하고 다음엔 다르게 시도할 텐데, 그 구조가 없었음.
LangGraph StateGraph에 Actor, Tool Executor, Evaluator, Reflection 4개 노드를 놓았다. Actor가 Thought → Action → Observation으로 추론하고, Tool Executor가 실행한 결과를 Evaluator가 평가한다. 평가는 두 단계 — 먼저 에러 키워드 규칙으로 빠르게 거르고, 통과하면 LLM이 정밀 판단. FAIL이면 Reflection 노드가 왜 실패했는지 분석해서 problem/solution 쌍으로 장기 기억에 저장한다. 다음에 비슷한 상황이 오면 Actor가 이 교훈을 꺼내 쓴다. 같은 실패가 계속되면 Early Stopping으로 끊는다.
Atelier 프론트엔드의 Product → Thread → Feed 계층 구조와 호환되는 17개 도구를 Tool Calling으로 실행. LLM은 Gemini, OpenAI, Anthropic 사이에서 YAML 설정만 바꾸면 전환 가능.

실패를 기록하고 재활용하는 구조가 돌아가면서, 같은 유형의 작업에서 재시도 횟수가 줄었다.

**Skylife 영화 추천 시스템** · Search

장르, 배우 같은 메타 필터만으로 추천하면 비슷한 결과만 반복됐음.
영화 메타 정보(장르, 내용 요약, 감독, 배우)를 임베딩 벡터로 만들어 PostgreSQL + pgvector에 저장. 추천을 2단계로 나눴다 — 먼저 메타 필터링(장르, 감독, 배우 조건)으로 후보를 줄이고, 그 안에서 영화 설명 벡터 유사도로 순위를 매긴다.

석사 때 연구한 임베딩-검색 파이프라인을 처음으로 실서비스에 적용한 프로젝트.

**부산관광공사 여행 스케줄링 챗봇** · Search · Service

기존 여행 검색은 "부산 / 1박 2일 / 맛집" 같은 고정 필터 수준이었고, "아이랑 갈 만한 조용한 곳" 같은 자연어 질의엔 대응이 안 됐음.
영화 추천에서 쓴 2단계 알고리즘(메타 필터 → 벡터 유사도)을 여행 도메인에 맞게 바꿨다. 메타 필터링은 지역, 숙박 일수, 카테고리, 벡터 유사도는 여행지 설명·후기·활용 정보로. 추천된 관광지를 바탕으로 일정 구성까지 한 번에 해준다.

현재 부산관광공사(Visit Busan)에서 상용 서비스로 운영 중.

**서울 상권분석 시스템 (sbiz_db + sbiz_llm)** · Pipeline · Agent

서울시 상권 데이터가 공개되어 있긴 한데, API 8개에 테이블 9개가 흩어져 있어서 SQL 모르면 사실상 못 쓴다. 자연어로 "강남역 카페 매출 추이" 같은 질문을 던지면 알아서 찾아주는 게 있으면 좋겠다 싶었음.
수집 파이프라인(sbiz_db)과 분석 에이전트(sbiz_llm)를 따로 만들었다. 수집 쪽은 서울 Open API 8개 서비스의 HTML을 APISpec 클래스로 파싱해서 스키마를 자동 추출하고, pandas로 컬럼 매핑(한글 → 영문) 후 PK 기반 UPSERT로 PostgreSQL에 넣는다. CLI(--sync-all, --validate 등)와 크론잡 지원.
분석 에이전트는 LangGraph 기반. 쿼리가 들어오면 라우터가 rag/chat/reject로 분기하고, 상권 질문이면 Tool Calling으로 9개 테이블(추정 매출, 점포, 유동 인구, 상주 인구, 직장 인구, 임대료, 상권 변화 지표, 집객 시설 등)에 PostgreSQL 동적 검색을 날린다. Tool Input은 Pydantic BaseModel로 정의, DB 접근은 asyncpg 비동기.

수집부터 자연어 분석까지 전부 혼자 만든 프로젝트. 상권 데이터를 SQL 없이 물어볼 수 있게 됐다.
